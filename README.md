# tick-store

tick-store is a C++23 columnar store for Nasdaq TotalView-ITCH 5.0 data. It stores a day's
268,744,780 messages in 1.76 GB, down from 8.25 GB. It gives every message back bit-exact. Beside
Parquet, ArcticDB and QuestDB on a 2018 four-core AMD Ryzen running Linux, it takes the least disk.
On the Ryzen it answers one stock's hour, warm, in 74.04 ms, though ArcticDB with a table per
stock is faster; ArcticDB or QuestDB wins short market-wide windows; the host was swapping memory
during some rivals' runs, which may flatter tick-store. One thread on the Ryzen ingests below
Nasdaq's published peak.

## What it is

A **record** is one ITCH message of the source file. The store holds one ITCH 5.0 day as columns
(`docs/store.md`) inside a container whose blocks each carry a CRC32C (`docs/format.md`). Records
are kept in segments of 2^22 by default, and a segment decodes from its own blocks alone. Linux
figures come from an AMD Ryzen Embedded V1605B, each run pinned: a benchmark to cpu4, the
comparison to cpu4 and cpu6. macOS figures come from an Apple M4 Max, unpinned.

- [RESULTS.md](RESULTS.md): every generated results table, every target with its verdict, the
  four-system comparison and the decode benchmarks.
- `BENCHMARKS.md`: the targets, and the published figure each one comes from.
- `docs/NOTES.md`: what was tried, including what did not help, with numbers.
- `docs/TASKS.md`: the plan.
- `docs/REVIEW.md`: the final review's findings, each with the test that
  showed it failing and the commit that fixed or closed it.

## Data

The data is Nasdaq's public TotalView-ITCH 5.0 sample files, which are not in this repository.
The reference day is 12302019, and 10302019 is the second day. `scripts/fetch_data.py`
downloads a day and verifies its size and SHA-256 against `scripts/data_pins.json`, which also
records each file's URL and message count:

```sh
python3 -I scripts/fetch_data.py --day all    # into data/
```

`tick_slice` builds the slice the benchmarks and the comparison's slice runs use,
`data/slices/12302019-open.itch`: every `S` and `R` message of the day, and the five minutes
from 09:29:30, as `scripts/data_pins.json` records.


## Build and test

What a build, the checks and the measurements need, each as a file in this repository gives it:

- **Compiler:** upstream Clang, with clang-tidy from the same LLVM. The results were built with
  Clang 23.1.4 ([RESULTS.md](RESULTS.md#benchmarks)), and fuzzing needs upstream clang, since Apple
  clang has no fuzzer runtime ([fuzz/README.md](fuzz/README.md#build)). It comes from the
  environment (`CC`, `CXX`), so nothing here names a toolchain path.
- **Build tools:** CMake 3.28 or newer (`CMakeLists.txt`) and Ninja.
- **Python:** `python3` for the scripts. The comparison's environment is Python 3.13, which
  `compare/setup.py` makes with `uv` ([compare/README.md](compare/README.md#setup)).
- **Check tools:** `scripts/check.sh` also needs `actionlint`, uses `shellcheck` through it, and
  runs `py-compare` in the comparison's `.venv`. `scripts/install_tools.sh actionlint shellcheck
  ninja llvm` puts actionlint 1.7.12, ShellCheck 0.11.0, Ninja 1.13.2 and LLVM 23.1.4 into the
  gitignored `.tools/`, each once its SHA-256 matches the pin in the script.
- **Data and disk:** the reference day is 3,524,013,057 bytes compressed and 8,251,407,909
  (8.25 GB) decompressed (`scripts/data_pins.json`, "Data" above). The full-day comparison also
  needs the day's export, 23.9 GB, and at least 50 GiB free on its work folder's disk
  ([compare/README.md](compare/README.md#full-day-comparison)).
- **Memory:** on the full day, `tick_roundtrip` peaked at 14,171,181,056 B resident on Linux
  (`systems.tickstore.peak_memory.vmhwm_bytes_by_process.tick_roundtrip` in
  `results/compare/Linux-12302019-full-ede0176b10bb.json`), and on the Mac its ingest at
  9,383,100,416 B and its verify at 11,346,673,664 B (`g1.ingest.peak_rss_bytes` and
  `g1.verify.peak_rss_bytes` in `results/roundtrip-12302019.json`), so a full day needs 16 GB of
  memory or more.
- **The headline figures:** the full-day comparison, `compare/run.py --day 12302019` with a
  `--variant-source`, as [compare/README.md](compare/README.md#full-day-comparison) gives it. It
  runs under the wrapper `TICK_STORE_MEASURE` names, which must take the machine, run its
  arguments, print a load line at each end, and exit 75 when it cannot have the machine
  ([Benchmarks](#benchmarks)).

```sh
cmake --preset dev && cmake --build --preset dev && ctest --preset dev
```

Presets, each building into `build/<preset>`: `dev`, `asan-ubsan`, `tsan`, `fuzz`,
`coverage`, `bench`. Every build preset caps itself at 6 parallel jobs. Fuzzing is described in
`fuzz/README.md`.

Fuzzing compares the SIMD kernels with the scalar ones on every codec block that ends within
an input's compare limit: 1,310,720 values from its start for the dictionary, and 2,097,152
for run-length and PFOR. Blocks hold up to 1,048,576 values, the format's largest.

The blocks within the cap also get the refusal, cut, block and column checks. A block is
within the cap while twice the values before it plus its own count stay within 262,144 values
(dictionary) or 1,048,576 (run-length, PFOR).

The re-encode checks take the first 5,123 values (dictionary) or 17,410 (run-length, PFOR),
and the first 64 values of each of the next 64 blocks.

Past the compare limit, PFOR decodes each block that ends within 3,145,728 values once, in
place, with the chosen kernel set; nothing more is examined.

The store writes codec blocks of 4,096 values, which every codec target takes whole as an
input's first block.

## Checks

`scripts/check.sh` runs every check, one step at a time, because a clang-tidy run and a
sanitizer build at once have run the M4 Max, which other work shares, out of memory. Every step runs even after
a failure. It then prints a summary table, and exits 1 if any step failed.

```sh
scripts/check.sh                          # everything
scripts/check.sh --quick                  # no sanitizers, fuzzing or coverage, and it says so
scripts/check.sh --fuzz-seconds 60        # each fuzz target's budget, 20 s by default
scripts/check.sh --only dev-test,hygiene  # chosen steps, plus the builds they need
scripts/check.sh --list                   # the step names
```

One full run on the Mac with a warm build tree took about 37 minutes by that run's log, which no
results file holds.

`CC`, `CXX` and `clang-tidy` come from the environment, from the same upstream LLVM. A missing
one is a clear error, and so is a missing `actionlint`, which `scripts/install_tools.sh
actionlint shellcheck` installs into the gitignored `.tools/` after checking its SHA-256. Raw
step logs go under `build/check/`, or `--log-dir` or `CHECK_LOG_DIR`.

The steps: the `dev` build with `-Wall -Wextra -Werror` and its tests, G-1 and G-2 through
`tick_roundtrip` on a small generated stream, with bit 1 of every byte of its store's footer
flipped in turn against G-2's rule, the `asan-ubsan` and `tsan` builds and their
tests, clang-tidy over all our C++, each libFuzzer target, coverage, the Python tests,
`scripts/check_results.py`, `scripts/check_compare.py`, `scripts/check_ties.py`, which fails
a results file once anything its figures were built and run from differs from the commit it
names (a file a validator's pin declares is reported as pinned, and a tree with no git history
is not judged; it compares sources, not built objects, since the build compiles the commit into a
generated source linked into every benchmark and the codec evaluation tools, so their binaries
differ between any two commits, and comparing the other objects would need both commits built in
one folder with one toolchain and would still say nothing of the Python harness that runs the
measurements), `scripts/render_results.py --check`,
which fails if the first screen's generated part or any table of RESULTS.md differs from a fresh
render, `scripts/render_writeup.py --check`, which fails if the essay, `WRITEUP.md`, differs from a
fresh render of its template and figure list and is not judged until every results file it reads
is committed, actionlint, and a check of what git tracks: no home path, no data file, nothing over 1 MB
but the named kinds of result, each argued for in the script, a JSON object and under 2 MB. No step loads a whole day. `ItchRealDay` reads the first 2 million messages.

`render_results.py --check`, `render_writeup.py --check` and `check_ties.py` hold the results
pages, the essay and the results files to more than a fresh render or a commit. Each has limits:
[docs/checks.md](docs/checks.md) says what each checks and what it does not.

A skip is never a pass. A step that cannot run shows as `SKIP`, as `py-compare` does with no
`.venv`, and a test skipped inside a passing step is named in that row. `ItchRealDay` skips
this way where the data is absent. The four sources a host does not compile, the other
operating system's two and the other processor's CRC32C and SIMD kernels, such as
`src/harness/page_cache_linux.cpp` on macOS, are named as not analysed by clang-tidy. The
`tsan` step and the coverage measurement leave out the fixed grid and the named seeds' tests,
which the unit and `asan-ubsan` steps run in full on each host (see `fuzz/README.md`, "Bounds").

A warning in a dependency cannot fail the build. `-Werror` is a `PRIVATE` option on our own
targets (`cmake/Warnings.cmake`), so a dependency's sources never see it, and FetchContent's
`SYSTEM` puts their headers on `-isystem`, which silences a warning from a header we include.
The fault `werror-dependency-tolerated` shows both: unused variables added to a GoogleTest
source and header print a warning and the build passes.

## Proof that each check can fail

A check that cannot fail proves nothing, so `scripts/prove_checks.py` shows each one failing on
an injected fault.

```sh
python3 -I scripts/prove_checks.py            # resumes, skipping what is already proven
python3 -I scripts/prove_checks.py --force    # redoes every fault
python3 -I scripts/prove_checks.py --only ubsan-shift-64
```

Each fault is a patch in `faults/` or a data mutation in the script. It runs in a throwaway
clone under `build/fault-proofs/`, never the working tree, and no production code knows about

## Round-trip check

Gates G-1 and G-2 of `BENCHMARKS.md`. `tick_roundtrip` stores a day in the ITCH store
(`docs/store.md`), then proves that every record comes back bit-exact. Fetch and verify the data
with `scripts/fetch_data.py` first, and take the pin from `decompressed_sha256` in
`scripts/data_pins.json`.

```sh
cmake --preset bench && cmake --build --preset bench
tools=build/bench/tools
day=data/12302019.NASDAQ_ITCH50
pin=5d81c2e14a0f748b29c674b6a342796932702034b4dd341e39e9a9ec5bac610f

$tools/tick_roundtrip ingest $day build/12302019.tsc --durability page_cache
$tools/tick_roundtrip verify $day build/12302019.tsc --expect-sha256 $pin
```

`ingest` takes the durability class, `page_cache` or `device_flush`, which is never a default,
and `--segment-records N`, by default 2^22. `verify` decodes the store segment by segment,
re-serialises every record through the ITCH encoder, and walks those frames and the source's in
lock step, comparing every byte, and hashes both whole streams on worker threads. Block CRCs are
checked as each block is read. It prints a JSON summary, with records, bytes, both hashes, the
verdict and the wall time. It exits 0 on a pass, 1 on a mismatch and 2 on a usage or I/O error. A
mismatch names the first difference: record index, source byte offset, bit, expected and actual
byte, and message type; a store error names the segment, column, block, file byte and record it
refused at.

To see it catch corruption, flip one bit of the store, where bit 0 is the least significant.
Flipping the same bit again restores the file. `layout --blocks` lists every block with its
segment, column and file offset, and `layout` shows the footer's offset. A flip inside a data
block is a CRC failure naming that block and its offset; with `--no-checksums` the decoder or the
oracle names the column and value, or the record, that came out wrong; a flip in the footer fails
the footer's CRC:

```sh
$tools/tick_roundtrip layout build/12302019.tsc --blocks > build/12302019-layout.json
$tools/tick_roundtrip flip-bit build/12302019.tsc 878213784 1   # segment 32's timestamp block
$tools/tick_roundtrip verify $day build/12302019.tsc --expect-sha256 $pin                  # exits 1
$tools/tick_roundtrip verify $day build/12302019.tsc --expect-sha256 $pin --no-checksums   # exits 1
$tools/tick_roundtrip flip-bit build/12302019.tsc 878213784 1
$tools/tick_roundtrip verify $day build/12302019.tsc --expect-sha256 $pin                  # exits 0
```

Byte 878,213,784 is the middle of segment 32's timestamp block, the middle segment of 65, in the
store `ingest` writes from the pinned day at the default settings; the writer is deterministic,
so the offset is the same on any host.

<!-- roundtrip:begin, generated by scripts/render_results.py, do not edit -->
On macOS, `ingest` took 96.6 s and `verify` 41.5 s; the store is 1.76 GB, 4.69 times smaller than
the day. `results/roundtrip-12302019.json` records all four.
<!-- roundtrip:end -->

`scripts/g2_plan.py` finds both flips from the store's listing by that rule: bit 1 of the middle
byte of the middle segment's first timestamp block, and bit 1 of the footer's middle byte. With
CRCs off, the reader skips the CRC32C of each block entry and each section entry in the footer, so
a flip there would go unseen; if the footer's middle byte falls in one, the flip moves on to the
first byte after it that the reader does read, as it did on `10302019`. The command
`python3 -I scripts/g2_plan.py build/12302019-layout.json build/g2.json`
prints the data and footer offsets `flip-bit` is given, and writes the `g2.json` that
`scripts/store_results.py` reads. That script assembles the published files from one day's
runs: each run's output, `/usr/bin/time -l` report and exit status in one folder, named as its
docstring lists, and `--build`, the build folder the tools ran from, whose preset it reads from
the folder's cache with `scripts/build_preset.py` and writes as `build_preset`:

```sh
python3 -I scripts/store_results.py build/roundtrip-raw --day 12302019 \
    --commit "$(git rev-parse --short HEAD)" --host macOS --build build/bench \
    --capacity results/fullday-capacity-12302019.json \
    --roundtrip results/roundtrip-12302019.json --size results/store-size-12302019.json
```

Results for both pinned days are in `results/roundtrip-12302019.json` and
`results/roundtrip-10302019.json`, with every byte of each store by column, section and footer in
`results/store-size-*.json`, and G-1 for one day on Linux in `results/roundtrip-12302019-linux.json`.
G-1 and G-2 are proved on the real store, not the stub: G-1 re-serialises every record the store
decodes and matches the whole stream's SHA-256 against the pin, and G-2 flips one bit in a data
block and one in the footer, each caught with CRCs on and with them off.

That is what G-2 shows: the two flips `g2_plan.py` plans, on each day's store. What other flips
do is known from two small stores, every bit of every byte flipped in turn, header to trailer,
in `tests/scripts/oracle_fixtures/all-bit-sweep.json`, whose counts
`tests/scripts/test_check_oracle.py` holds. With CRCs on, every flip is caught. With them off, a
flip in a block or section entry's CRC32C or in the trailer's footer CRC32C passes, since nothing
reads them then, and so do 57 of the 5,920 bit positions of the smaller store's block payloads
and 74 of 22,592 of the larger one's, 0.96% and 0.33%, each leaving every record intact; every
other footer bit is caught. The footer flip is steered past the CRC32Cs; the data flip is not
steered, and was caught on both days.

`tick_roundtrip ingest-stub` still writes the [Phase 2](docs/TASKS.md#phase-2-harness-before-any-implementation) stub store, the day's frames behind a
40-byte header with no checksum, which `verify` recognises by its magic.

`tick_census <source> <output.json>` writes the aggregate statistics in `results/`.
`results/codec-eval-<day>.json` is `tick_codec_eval`'s output with the build's preset and its
peak memory added by `scripts/codec_eval_results.py`, which reads the preset from the build
folder's cache:

```sh
/usr/bin/time -l -o build/eval.time $tools/tick_codec_eval $day build/codec-eval.tool.json \
    --day 12302019 --prove-all-price4
python3 -I scripts/codec_eval_results.py --tool-output build/codec-eval.tool.json \
    --time build/eval.time --build build/bench --out results/codec-eval-12302019.json
```

`tick_slice <source> <output> [--from HH:MM:SS] [--to HH:MM:SS]` writes a small valid
stream for the comparison harness: every `S` and `R` of the day plus one window.

## Benchmarks

`bench/itch_codec_bench` measures ITCH decode, and decode then encode, over the pinned
slice, `data/slices/12302019-open.itch`. Build the slice with `tick_slice` as
`scripts/data_pins.json` records. `scripts/run_bench.py` drives the benchmark and writes
one results file per host, `results/bench/<host>-<benchmark>-<commit>.json`:

```sh
cmake --preset bench && cmake --build --preset bench
TICK_STORE_MEASURE=/path/to/measure.sh \
    python3 -I scripts/run_bench.py build/bench/bench/itch_codec_bench
python3 -I scripts/check_results.py results/bench/*.json
python3 -I scripts/render_results.py
```

Two more binaries measure decoding, for `BENCHMARKS.md`'s decode targets, which say which
case answers which target. `bench/simd_kernel_bench` times each decode kernel of each set on
seeded input, one vector of 1,024 values in L1 (input kind `seeded`), and
`bench/column_decode_bench` times real columns built from the same slice (input kind
`column`): its add-order prices and timestamps, Gorilla against the store's own layout. Both
count values, not messages, and run the same way:

```sh
TICK_STORE_MEASURE=/path/to/measure.sh \
    python3 -I scripts/run_bench.py build/bench/bench/simd_kernel_bench
TICK_STORE_MEASURE=/path/to/measure.sh \
    python3 -I scripts/run_bench.py build/bench/bench/column_decode_bench
```

A kernel case is checked against the scalar set's output, or for `dod_reconstruct` against the
sequence it came from, before timing and after; `--verify-all` does that for every case at
every width, and ctest runs it. A column case runs only once the slice matches its pin and the
decode gives its column back bit for bit, and records the column's encoded size, so its
results carry a ratio. RESULTS.md gives a column file a row a case, and a kernel file a row a
kernel and set, the median across the widths it ran.

`TICK_STORE_MEASURE` names a wrapper that takes the machine, runs its arguments and prints
a load line at each end. Exit 75 from it means retry later. Without the variable there is
no lock, so the file is marked iteration-only, goes under `build/`, and the validator
refuses it. On the measured hosts the wrapper was `measure.sh`, the machine's
measurement lock, which runs one measurement at a time, with the governor set on Linux; it is not
in this repository. Each case runs as its own process, so `perf stat` counts one workload. On
Linux, the case runs on `cpu4` under `taskset`, and `perf` counts only the timed passes.
Nothing keeps that core's SMT sibling idle, so each case records in `sibling_busy_percent`
how busy the sibling was, from `/proc/stat` once the lock is held and again at the end. The
validator refuses a reported result where it exceeds 5% in any case. I chose that limit; it is
not a measured threshold.

Before any time counts, the input must match its SHA-256 pin, and decoding then encoding
it must rebuild exactly those bytes. Each timed pass is checked afterwards too. Batch
times go into an HdrHistogram in timer ticks. Nothing is published below 10 timer steps
or 5 timer reads: the binary refuses to, and the validator refuses the file.

The tables are generated from the results files by `scripts/render_results.py`, into
[RESULTS.md](RESULTS.md#benchmarks). These numbers are harness evidence, not targets:
`BENCHMARKS.md` holds the targets.

## Comparison

`compare/run.py` runs tick-store, Parquet, ArcticDB and QuestDB on the same slice, and on
Linux on a whole day, and writes one file per host and input to `results/compare/`, which
`scripts/check_compare.py` must pass. `compare/README.md` describes the method: the durability
classes, how each setting is read back, the read-back oracle, the queries and how warm and cold
are proven. The tables, and what is needed to read them, are in
[RESULTS.md](RESULTS.md#comparison).

On the Linux full day the systems' write clocks do not start alike, and every write verdict against
another system is given with that beside it. Write inputs are not alike on this day, by each
write's record: tick-store's input is in memory before the clock starts, and Parquet's, ArcticDB's
and QuestDB's are read from disk inside it, with 18,411,094,016 to 24,631,062,528 B read from the
device inside those headline write clocks of class A and B against 250,916,864 to 274,239,488 B
inside tick-store's; engine-only, the clock less reading the input and putting it in the form the
system's call takes, may still hold those reads, which are counted over the whole clock, so the
two-clock rule does not take the difference out.
