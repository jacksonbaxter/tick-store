### 1.2 Data types and field semantics

Fields common to the records in this subsection: URL is the spec URL above; hardware n/a; data set n/a (format specification, newest revision April 28, 2023); applicability is direct, the decoder and columns follow from these.

- **D1 Byte order.** Value: big-endian, unsigned unless noted. Quote: "All integer fields are big endian (network byte order) binary encoded numbers." Location: p. 4, Data Types.
- **D2 Alpha fields.** Value: ASCII, left-justified, right-padded with spaces. Quote: "All alpha fields are ASCII fields which are left justified and padded on the right with spaces." Location: p. 4.
- **D3 Price(4).** Value: integer with 4 implied decimals; maximum 200,000.0000 = 2,000,000,000 raw (0x77359400; arithmetic checked). Quote: "a field flagged as Price (4) has an implied 4 decimal places." and "The maximum value of price (4) in TotalView ITCH is 200,000.0000 (decimal, 77359400 hex)." Location: p. 4. Note: the maximum fits a signed 32-bit integer; the field is 4 bytes and unsigned by D1.
- **D4 Price(8).** Value: integer with 8 implied decimals, 8 bytes wide, used only by the three `V` levels. Quote: "When converted to a decimal format, prices are in fixed point format, where the precision defines the number of decimal places." (p. 4); "Level 1 11 8 Price (8) Denotes the MWCB Level 1 Value." (p. 10). The 8 decimals are the reading of the general rule applied to the type name; no sentence states "8 decimals" and no maximum is stated. `V` occurs once a day on the censused days below.
- **D5 Timestamp.** Value: 6-byte unsigned integer at offset 5, nanoseconds since midnight. Quote: "Timestamps are represented as nanoseconds since midnight" (p. 4). Width and offset come from the field tables, not prose. Time zone: not stated in the spec. Derived: 86,400 × 10^9 = 8.64 × 10^13 < 2^47 = 1.407 × 10^14, so a real timestamp never sets the top bit of the 48.
- **D6 Stock Locate.** Value: 2-byte integer at offset 1 in every type, assigned daily from 1, 0 when not stock dependent. Quotes: "The locate codes are dynamically assigned each day, starting with a value of 1" and "A default value of 0 will be applied to messages which are not stock dependent." Location: p. 3. Type tables say always 0 for `S` (p. 4), `V` (p. 10), `W` and `K` (p. 11); `K` carries a Stock field and still says "Always set to 0", so do not assert this, store the bytes.
- **D7 Tracking Number.** Value: 2-byte integer at offset 3 in every type. Quote: "Nasdaq internal tracking number". Location: every type table; revision log p. 24 "Addition of an internal tracking number to multiple messages". The spec defines no semantics, range or ordering. Treat as opaque. See F7 for what was observed.
- **D8 Order Reference Number.** Value: 8 bytes; day-unique; increase is not guaranteed. Quotes: "day-unique Order Reference Number" (p. 12); the guarantee was removed in 2009: "to remove the following statement: “The order reference number is increasing, but not necessarily sequential.”" (p. 26, entry February 3, 2009).
- **D9 `U` introduces a new reference.** Quote: "a new order reference number which will be used henceforth." (p. 15); Original 11/8 and New 19/8 (p. 16). `U` has neither side, stock nor MPID: "Firms should retain the side, stock symbol and MPID from the original Add Order message." (p. 16).
- **D10 `P` fixed-value fields.** Quote: "the field will be null" (p. 17, continuing from p. 16: Order Reference Number populated as zero, effective December 6, 2010) and "this field will always be “B” regardless of the resting side" (p. 17, effective 07/14/2014). So `P` carries 8 zero bytes and a constant side on sessions after those dates, by specification. Do not rely on it; check at ingest and keep exceptions.
- **D11 `H` Reserved byte.** Value: 1 byte at offset 20, Alpha. Quote: "Reserved 20 1 Alpha Reserved." (p. 8). Its content is not stated. It must be stored even though it has no meaning.
- **D12 Wide share fields.** `Q` Shares is 8 bytes (p. 17) and `I` Paired and Imbalance Shares are 8 bytes (p. 19), while `A`/`F`/`P`/`U`/`E`/`C`/`X` share fields are 4 bytes. A single 32-bit shares column cannot hold them.
- **D13 Match Number.** Value: 8 bytes in `E`, `C`, `P`, `Q`, `B`. Quote: "The Nasdaq generated day unique Match Number of this execution." (p. 14).
- **D14 End of day.** Quote: "End of Messages. This is always the last message sent in any trading day." (p. 5, event code `C`). This is the only completeness signal the sample files actually carry; see section 3.
- **D15 Enumerations are open sets for storage.** The Message-type and enum lists are a snapshot of the spec. New code `P` for Imbalance Direction and the `O` message arrived in the April 28, 2023 revision (p. 22); Extended Trading Close Cross Type `A` arrived January 7, 2022 (p. 22). A store that encodes these as closed enums would fail on later files; store raw bytes.
- **D16 Text in the spec that disagrees with its own tables (does not change a length).** `K` IPO Price note describes ASCII padding although the type is Price (4) (p. 11). `O` event text says "Outside of time stamp messages" although 5.0 has no timestamp message (p. 5). `Q` table on p. 17 is titled "Trade Message (Non-Cross)"; `W` table on p. 11 is titled "MWCB Decline Level Message".
- **D17 Fixed lengths per type.** Quote: "Each message is variable in length based on the message type." (p. 3). The spec never prints a total length and never mentions a length prefix (grep of spec.txt for "prefix" and for BinaryFILE returns nothing; see F1).

## 3. File framing and what a bit-exact round trip must preserve

### 3.1 Framing sources

- **F1 ITCH spec is silent.** The spec never mentions a length prefix or BinaryFILE (D17). Framing comes only from the file format document.
- **F2 BinaryFILE.** Value: each message is a 2-byte big-endian payload length, then the payload. Quote: "The messages are variable length and include a two byte big-endian length that indicates the length of the payload" Location: binaryfile.pdf p. 1, section 1.1. URL: https://m.nasdaqtrader.com/content/technicalSupport/specifications/dataproducts/binaryfile.pdf (BinaryFILE Version 1.00; cached CACHE/downloads/binaryfile/binaryfile.pdf, SHA-256 `a1f443400728b3ce44953e9ae263e4846fe6ad68420e7a635829872aefdfff60`). Applicability: direct.
- **F3 The Nasdaq FAQ points sample readers to BinaryFILE.** Quote: "Information on how to read these files can be found via the BinaryFILE specifications" Location: ITCH_FAQ PDF p. 2 (URL in L1). ITCHFTP p. 3 for the paid product: "firms should use the BinaryFile protocol to process the TotalView-ITCH 5.0" files (URL in L8; the sentence wraps across lines).
- **F4 The length excludes itself.** BinaryFILE says "the length of the payload". MoldUDP64 is explicit: "The message length field value does not include the two bytes occupied by the message length field." Location: moldudp64.pdf p. 4. URL: https://www.nasdaqtrader.com/content/technicalsupport/specifications/dataproducts/moldudp64.pdf (cached CACHE/downloads/moldudp64/). Note the contrast with SoupBinTCP, whose length counts the packet type byte: "the length of rest of the packet" (soupbintcp.pdf p. 2, https://www.nasdaqtrader.com/content/technicalsupport/specifications/dataproducts/soupbintcp.pdf). A sample file has no SoupBinTCP type byte. So the ITCH type byte is byte 0 of the payload and the prefix value equals the spec length. `00 0c` = 12 for `S`.

### 3.2 What a bit-exact round trip must preserve

Facts above, then consequences. The consequences are my reading for the plan, not sourced statements.

1. **Global message order.** The stream is "a series of sequenced messages" (spec p. 3) and its sequence numbers are implicit: BinaryFILE carries none, and in SoupBinTCP "Sequenced Data Packets do not contain an explicit sequence number" (soupbintcp.pdf p. 3). A file ordinal is the only total order. Timestamps cannot rebuild it because several messages can share one nanosecond (T2). Splitting by type or by locate therefore needs a stored permutation or per-row ordinal, and its cost belongs in the compression numbers.
2. **Length prefix.** Implied by type if and only if the frame length equals the spec length. Evidence says it always does on three days (table above), but BinaryFILE defines no maximum and Nasdaq adds types (`O` in 2023). Keep an exception path that stores the prefix and raw payload for any unknown type or length.
3. **Type byte, Stock Locate, Tracking Number, Timestamp** in every record, 11 bytes per message.
4. **All body bytes, including ones with no meaning**: `H` Reserved (D11), `P` zero order reference and constant side (D10), `R` flags and enums (F8), space padding in Stock, MPID/Attribution and Reason (D2).
5. **Redundant Stock.** Stock appears in `A F P Q R H Y L J K h I N O`, usually implied by locate. astra reports `order_add_stock_mismatches=0` on S061226 (trace profile line 2, claim), which covers adds only. Dictionary-encode against locate only with a per-record check and an exception path.
6. **File tail.** No terminator and no trailing bytes on the days above, but the format allows both. Store whatever follows the last whole frame verbatim, zero or more bytes, so a future file with a terminator also round-trips. Completeness is last message = `S` code `C` (D14), since a truncated file is otherwise a well-formed prefix (carteret data.md lines 245-247).
7. **Is every byte covered by a column?** Yes if and only if: frame prefix (implied or exception), each of the fields in table 1.1 by type, and the tail. Table 1.1 has no gaps: the fields are contiguous from offset 0 to the message end for all 23 types, so no hidden padding exists inside a message by specification.
8. **The gzip container is out of scope.** The round trip target is the decompressed stream. The `.gz` bytes cannot be regenerated from messages without the original compressor and settings. Pin both hashes.
9. **Compare at both levels.** Per-record comparison proves each record. A SHA-256 of the whole re-serialised stream against the source also proves order, prefixes and tail, which per-record comparison alone could miss.

## 6. Tick-storage prior art

Applicability overall: no source below stores ITCH bit-exactly in a columnar system. All ratios are context, unless marked direct.

- **A1 Databento DBN.** Value: `MboMsg` is 56 bytes per record (fixed), 16-byte `RecordHeader` first. Quote: "const _: () = assert!(std::mem::size_of::<MboMsg>() == 56);" Location: rust/dbn/src/record.rs line 125; cached copy is byte-identical to main on 2026-10-30. URL: https://github.com/databento/dbn/blob/main/rust/dbn/src/record.rs (cached CACHE/downloads/dbn/record.rs). Design quote: "DBN strictly uses fixed lengths and offsets for all fields." Location: "Highly compressible" bullet. URL: https://databento.com/docs/conventions/databento-binary-encoding (cached CACHE/downloads/databento/Databento-binary.txt, lines 81-83). Hardware: not stated. Data set: format fact. Applicability: design precedent, row-oriented, and it is not a byte-preserving ITCH store: fields are normalised (price scale 1e-9, `ts_event` since UNIX epoch, a venue `sequence`, no Tracking Number or Stock Locate). 56 bytes against ITCH mean 30.6 to 31.9 bytes per framed message (4.1): the raw file is the smaller row format. itch-book reports Databento "models an ITCH replace as a cancel plus an add" (README line 393), so record counts differ too.
- **A2 Databento zstd.** Value: "nearly 4x" decompression speed against zlib at the same ratio. Quote: "At the same compression ratio, we've found it decompresses nearly 4x as fast as zlib on a single core." Location: blog body. URL: https://databento.com/blog/zstd-vs-zlib (cached CACHE/downloads/databento/zstdblog.txt.plain). Hardware: not stated. Data set: not stated. Counted: not stated. Applicability: context only. No DBN compression ratio or bytes-per-record figure for XNAS.ITCH was found.
- **A3 Man Group Arctic (original).** Value: "~10x" on network and disk. Quote: "achieves ~10x compression on network bandwidth, ~10x compression on disk" Location: PyPI project description, version 1.80.4. URL: https://pypi.org/project/arctic/1.80.4/ (cached CACHE/downloads/arctic-pypi/arctic-1.80.4.json). Hardware: not stated. Data set: not stated. Counted: not stated. Applicability: context, an unqualified claim that covers Arctic generally, not TickStore on ticks. The latest PyPI description (1.82.2) no longer carries the sentence.
- **A4 Arctic TickStore design.** Facts from source, no ratio: default chunk 100,000 rows (`chunk_size=100000`, tickstore.py line 114); each column stored separately and LZ4-HC compressed (`lz4_compressHC`, lines 722, 767); row masks packed for sparse columns (lines 711, 761); index stored as first value plus `np.diff`, at millisecond resolution (`datetime64[ms]`, lines 728-731), decoded with `np.cumsum` (line 460). URL: https://github.com/man-group/arctic/blob/master/arctic/tickstore/tickstore.py (cached CACHE/downloads/arctic/tickstore.py). Quote: "Column oriented tick database." (README-arctic.md line 100). Applicability: design precedent for per-column delta plus block LZ on fixed chunks; millisecond index cannot hold ITCH nanoseconds; repository is in maintenance mode.
- **A5 LOBSTER.** Value: CSV, per ticker and day, `message` and `orderbook` files. Prices use the same scale as ITCH: quote: "Dollar price times 10000 (i.e. a stock price of $91.14 is given by 911400)" Location: output structure page. Time in seconds with decimals "up to nanoseconds depending on the requested period". Message file columns: Time, Event Type, Order ID, Size, Price, Direction. Sample zip sizes, 2012-06-21: AAPL 1.3 / 4.2 / 6.5 MB at 1 / 5 / 10 levels; AMZN 0.7 / 2 / 4; GOOG 0.5 / 1.6 / 2.5; INTC 3.3 / 5.8 / 6.7; MSFT 3.3 / 5.9 / 7.2. Location: data samples page table, snapshot 2023-05-31. URL: https://web.archive.org/web/20230531224640/https://lobsterdata.com/info/DataSamples.php (cached CACHE/downloads/lobster/ws-DataSamples.html; structure page ws-DataStructure.html). Hardware: n/a. Counted: zip size of the sample, row counts not stated. Applicability: context; reconstructed subset, drops bytes, not a compression study. Quote on source: "All sample files are based on the official NASDAQ Historical TotalView-ITCH sample."
- **A6 LOBSTER-style export size.** Value: 66 to 92 MB of messages and 310 to 558 MB of orderbook per symbol at ten levels, AAPL, MSFT, SPY, 1.25M to 2.19M rows, CSV. Quote: "(66 to 92 MB of messages, 310 to 558 MB of orderbook per symbol)" wraps across lines. Location: itch-book README lines 214-216. Hardware: 9950X3D per README. Data set: 12302019. Applicability: context only.
- **A7 kdb+ FSI compression case study.** Data set: NYSE TAQ, one day in 2022. Quote: "Table quote had 1.78 billion rows and consumed 180 GB disk space uncompressed." and trade "contained 76 million rows and required 5.7 GB space". Location: Appendix, data description. URL: https://code.kx.com/q/kb/compression/fsicasestudy/ (cached CACHE/downloads/kdb/fsicasestudy.html). Hardware: Intel Xeon 6780E with NVMe, and Xeon 6747P with NFS (ratios are hardware-independent). Block size: "logical block size of 128 KB". Parted by Symbol. Exact text claim: "zstd outperforms lz4 and snappy by nearly 2x, though it is only marginally better than gzip". Column-level relative size in % (exact, tables `quote` and `trade`), gzip 6 / lz4 9 / snappy / zstd 1 / zstd 14 / zstd 22:
  - quote.Time 36.3 / 60.5 / 62.4 / 31.3 / 33.8 / 33.8; Participant_Timestamp 45.0 / 69.0 / 71.5 / 41.3 / 41.0 / 41.0; Sequence_Number 41.2 / 100.0 / 100.0 / 81.4 / 35.1 / 36.8; Offer_Price 6.6 / 10.1 / 15.9 / 7.7 / 6.1 / 5.6; Offer_Size 14.3 / 19.2 / 34.3 / 16.3 / 12.7 / 11.8; Symbol 0.2 / 0.4 / 4.7 / 0.1 / 0.0 / 0.0.

Timestamps stay at 31 to 45% of raw with block compression alone, which is the gap delta coding has to close. Derived: quote table about 101 bytes per row uncompressed.
- **A8 Parquet on ITCH-derived tables.** Value: BX 2019-07-30 converted to `bbo` 267 MB and `trades` 15 MB, Parquet zstd, from a 391 MB gzip source. Quote: "The BX day above converts to `bbo` (267 MB) + `trades` (15 MB) in 6.6 s" Location: itch-book README lines 197-198; row counts line 170 (19.1M `bbo`, 925k `trades`). Derived: about 14.0 bytes per `bbo` row, 16.2 per `trades` row. Applicability: closest published columnar size on ITCH-derived data; lossy for tick-store's purpose, so not a target. `messages` table Parquet size: not stated.

Data set: Nikkei NEEDS tick CSV, 95 columns. Applicability: context only, and the baseline is text CSV, not binary; do not compare with A9.
